# 面试演示脚本

## 60 秒版本

1. 打开应用，说明问题：反馈散落在多个渠道，只看正负情绪无法确定优先级。
2. 保持“使用演示数据”，点击“开始生成洞察”。
3. 切到“洞察报告”，展示有效反馈数、主题数、最高优先级和审核状态。
4. 展开“稳定性与故障”，指出每条结论都有代表原话、来源和反馈 ID。
5. 切到“人工审核”，说明为什么高风险结论必须人工确认。
6. 下载 Markdown 报告或打开历史记录，展示分析留痕。

## 3 分钟版本

### 背景

“我在看 AI 产品运营岗位时发现，很多作品只会让大模型生成情感分析。但运营真正要解决的是：哪些问题值得先修、证据是什么、结论能不能让团队相信。”

### 方案

“所以我把流程拆成清洗与脱敏、主题归类、证据保留、优先级排序、质量门禁和人工审核。模型只负责逐条语义分类，最终结构由代码约束，避免自由生成失控。”

### 可靠性

“如果没有 API Key 或模型输出不合格，系统会自动回退到本地规则。高严重度或低置信度结果会被强制提示审核，而不是直接当成最终结论。”

### 评测

“我准备了三套数据。前两套在调规则阶段会达到很高结果，但未参与调规则的发布测试只有 57.1%，说明关键词规则泛化不足。所以我没有拿 100% 做宣传，而是把规则定位为可复现兜底，主模式使用大模型语义分类。”

### 产品判断

“这个项目最大的取舍是先完成业务闭环，而不是先堆 LangGraph、向量数据库和多智能体。对目标岗位来说，能否解释质量、证据和人工介入比技术名词更重要。”

## 常见追问

**这算 Agent 吗？**

项目具备模式路由、结构化校验、失败重试、自动回退、人工审核和质量门禁，是一个有边界的工作流 Agent。它不是能自主完成任意任务的多智能体系统。

**为什么不用向量检索？**

当前输入是待集中分析的反馈，不是大规模知识库问答。优先级更高的是分类质量、证据追踪和人工审核；数据规模增加后再考虑聚类和向量检索。

**为什么本地规则准确率低还保留？**

它保证无 Key 演示、隐私敏感场景和模型故障时仍能运行，同时提供可复现的对照基线。项目没有把低精度规则包装成最终能力。

**如何继续迭代？**

接入真实匿名反馈，建立人工金标集，比较关键词、Embedding 聚类和 DeepSeek 分类的准确率、成本、延迟和人工采纳率，再根据数据决定默认方案。
